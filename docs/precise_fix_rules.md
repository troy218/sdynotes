# 버그 고치는 방법 — 「정확히 지우고 정확히 다시 쓴다」 (공동 원칙)

> 이 문서는 **모든 수정(PR)이 따라야 할 규칙**이다. 2026-09 에 사용자가 받은
> 요청 그대로를 원칙으로 적는다:
>
> *"줄만 많이 적어서 코드를 크게 만드는 게 아니라, 틀린 부분은 제대로 지우고
> 다시 정확한 코드를 적는 방식으로 고쳐줘."*
>
> 요약하면 — **덧붙이지 않는다. 바꾼다.** 방어 코드·중복 가드·특수 케이스
> 분기를 더해서 코드가 자라는 수정은 리뷰에서 거부된다.

## 1) 다섯 가지 규칙

1. **근본 원인을 먼저 찾는다.** 증상이 나오는 코드가 아니라, 잘못된 데이터를
   만들어 낸 *한 곳*을 찾는다. 이 저장소의 버그는 대부분 "한 줄이 틀려서
   데이터가 오염되고, 오염된 데이터가 여러 증상으로 퍼져 보이는" 구조다.
   증상(예: "상자가 사라진다", "쪽이 겹친다")을 각각 고치려 들지 말고
   오염원을 고른다.
2. **틀린 줄을 지우고 그 자리에 정확한 코드를 쓴다.** 같은 자리에서
   `if` 하나를 고칠 수 있는 것을, 바깥에 가드를 하나 더 두는 방식으로
   풀지 않는다. 결과적으로 diff 는 **삭제 줄 수 ≈ 추가 준 수**가 돼야 한다.
3. **살려야 하는 동작을 먼저 적는다.** 지우기 전에 그 코드가 왜 존재했는지
   (주석·계약 테스트·재현 스크립트) 확인하고, 고친 뒤에도 그 의도가
   살아있는지 테스트가 지켜본다. 지우기만 하면 회귀, 덧붙이기만 하면
   기술부채 — 둘 다 실패다.
4. **재현 테스트가 먼저, 수정이 나중.** 고치기 전에 실패하는 재현을 만들고
   (짧게 — 서버 띄우는 런타임 테스트 하나면 충분), 고친 뒤 같은 테스트가
   통과하는지 본다. 재현이 없는 수정은 "고친 것 같은" 수정이다.
5. **테스트는 시간을 아끼게.** 전체 `npm test` 는 배포 직전에만 돌린다.
   평소에는 ① 소스 계약(contract) 테스트(초 단위) → ② 관련 런타임 그룹
   하나(`npm run test:pages` 처럼, 10~20초)면 충분하다.

## 2) 이 번(14.23.1) 수정이 규칙을 적용한 실례

증상(사용자 보고 — 쪽 많은 논문을 읽을 때):
- 텍스트상자를 누르면 그 상자가 사라진다
- 여러 쪽의 내용이 한 쪽에 겹쳐 나온다
- 해돌이 「이 페이지」 정리가 첫 페이지만/엉뚱한 쪽을 요약한다

근본 원인은 **두 줄**이었다 (증상은 여럿이었지만):

| # | 틀린 코드 (지움) | 정확한 코드 (그 자리에) | 근데 어쩌다 이런 증상까지? |
|---|---|---|---|
| 1 | `loadDocAsync` — 마지막으로 보던 슬라이스(`?from=N`)를 받아 `pages[0]`부터 넣음 | 받은 슬라이스를 `pages[firstSlice+k]` **원래 자리**에 놓고 나머지는 `lazy_k` 스텁으로 채움 | 앞 8쪽 자리에 마지막 슬라이스가 끼워지고, 뒤에서 같은 슬라이스가 또 로드돼 **같은 내용이 두 번**·슬라이스 재수신 시 `loadBatch`의 id-보강 경로가 **서로 다른 쪽의 글상자를 한 쪽에 합침** → 렌더·저장 시 `sanitizePageEls`가 겹친 상자를 **삭제** → "상자가 사라진다" |
| 2 | `saveLastPos` — 노트가 열리는 시퀀스(`curPageIdx=0`)에서도 저장값을 덮어씀 | `_posReady` 플래그: `restoreLastPos`가 저장값을 읽고 난 뒤에만 쓴다 (노트 열 때 플래그 리셋) | 마지막으로 본 쪽이 매번 0으로 초기화돼 **재접속 때마다 1쪽에서 다시 시작** → 「이 페이지」도 1쪽 글을 보내기 일쑤 |

두 군데를 고치자 세 증상이 같이 사라졌다. 증상별로 코드를 덧붙이는 길은
쓰지 않았다. 회귀 방지: `test/editor_lazy_reopen_runtime.mjs`
(`npm run test:pages` 그룹, 약 10초).

## 3) 금지 목록 (리뷰 거부 사유)

- 증상을 감싸는 `try/catch`·`if` 가드 추가로 "터지지만 않게" 만들기
  (원인은 그대로 살아있음)
- 같은 판단을 두 곳에서 하는 중복 가드 ("혹시 몰라서 하나 더")
- 옛 버그가 남긴 오염 데이터를 순회해서 고치는 '청소 코드'를 로드 경로에
  두기 (새 데이터는 애초에 오염되지 않게 **만드는 곳**을 고친다)
- 수정 줄 수가 삭제 줄 수보다 눈에 띄게 많은 버그 패치

## 4) 남은 알림 (이 번 수정의 경계)

- 옛 버전이 이미 **서버 슬라이스까지 오염 저장**한 문서는 원본 PDF 를 다시
  가져오는 것만이 완전한 복구다 (서버 원본이 덮여졌으므로).
- 기기 캐시(localStorage `nb_*.pages`)에 오염 배열이 남은 문서는 스크롤로
  멀어졌다 돌아오면(evict → 재수신) 자연히 정렬된다.
