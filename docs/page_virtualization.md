# 대용량 노트(500쪽+) 페이지 열람 설계 — '셸 가상화'

`sdynotes.js` 의 에디터 본문(`#pagesStage`) 렌더 구조 설명서. 현재 기준은 **14.35.0**이며, 아래의 이전 버전 측정은 역사 기록이다.

## 14.35.0 읽기 화질과 편집 준비의 분리

이전 테스트는 읽기 스크롤 또는 **이미 만들어진 일반 텍스트 DOM**에서 시작했다.
실제 문제였던 가져온 페이지의 **첫 포인터 → 단어 span 생성 → 폭 맞춤 → 선택**은
포함하지 않았다. 이제 이 전환을 독립적으로 검사한다.

### 상태와 수명

```
읽기(쪽 그림 한 장)
  ├─ 180ms 유휴 + 스크롤 종료 → 필요한 화질의 그림으로 decode 후 교체
  └─ 클릭/편집 도구 → 준비 중(그림 유지, aria-busy)
                        ├─ 문서·렌더 버전·종이 신원이 그대로 → 준비 완료 → 첫 동작 전달
                        └─ 언마운트/노트 전환/재렌더 → 이전 작업 취소
```

- `activatedPages`는 활성화 **요청**, `renderedPages`는 내용 DOM을 가진 쪽(부분 포함),
  `_pageRenderJobs`는 진행 중 작업이다. **완료 판정은 `pageReady(pi)`**를 사용한다.
- `activatePage(pi)`는 중복 호출을 합쳐 `Promise<boolean>`을 돌려준다.
  DOM이 필요하면 완료를 기다린다. 실패/취소는 `false`이며 lazy 로드 실패를 재귀 렌더로
  재시도하지 않는다. `renderPageEls(pi)`는 명시적 재렌더로 기존 작업을 교체한다.
- 작업은 문서 객체, 캡처한 render version, 종이 노드 및 쪽 데이터 신원을 확인한다.
  닫기/재렌더는 렌더·글자 맞춤·포인터·화질 예약을 정리한다. 늦은 이미지 오류나 응답은
  새 노트를 오염시키지 않는다. 준비 중 원격 갱신도 이전 청크와 섞지 않는다.
- 첫 클릭은 선택, 더블클릭은 편집, 도구 클릭은 해당 도구의 기존 핸들러에 전달한다.
  준비 중 첫 펜 획의 포인터 샘플도 보존한다. 읽기 터치는 **up 전에는 준비를 시작하지 않고**,
  이동/휠/scroll/pointercancel/Escape/다른 노트·도구에서는 보류한 동작을 취소한다.
  스크롤을 막는 문서 전체 로딩 덮개는 없다. 실제 뷰포트 이동으로 취소하며, 누르기 전에
  예약됐던 무이동 scroll 알림이 늦게 왔다고 새 클릭을 버리지 않는다.
- 선택/맞춤만 한 쪽은 회수 시 읽기 상태로 복귀할 수 있다. `edited`/`__dirty`인 쪽은
  원본 미리보기로 복귀하지 않는다. 펜·표·그림·이동/삭제·그룹·메모 수정과 전체 undo도 해당
  쪽을 저장 대상으로 표시한다. 실제 텍스트 입력과 undo/redo는 기존 요소 패치/저장 경로를 쓴다.

### 작업 예산과 데이터 안전

- 렌더: 모든 진행 중 쪽이 **공유하는 5ms 협력적 예산**과 청크당 HTML 가중치 약 12KB.
  단순한 작은 노트는 동기 렌더 호환을 유지하지만, 문단 개수만 보고 무거운 쪽을 동기로
  만드는 120개/고정 CHUNK 정책은 제거했다. 요소 내부의 마크업 길이와 획 점 수도 고려한다.
- 단어 맞춤: 읽기 프레임과 쓰기 프레임을 분리한다. 측정 커서와 쓰기 커서를 기억해
  **한 문단 안에서도 재개**, 쓰기는 프레임당 최대 80단어다. 스크롤/DOM 준비 중에는
  기다리고, 회수된 쪽의 예약은 삭제한다. 원문·크기·글꼴·굵기·폰트 로드 세대로 캐시한다.
- `_sdyViewHtml`로 표시용 HTML을 구분한다. 폭 맞춤이 `el.html`이나 `__lastHash`를
  변경해서 저장/협업에 섞이지 않는다. 편집 후 무입력 커밋과 소수점 글자 크기도 보존한다.
- 페이지 전체 후손을 무효화하던 이미지 선택 `:has()` 안전망을 제거했다. 레이어는 원래
  항상 보이는 구조이며 선택은 기존 z-index 승격을 쓴다. 드래그 선택 방지도 모든 단어의
  `*` 규칙 대신 본문 컨테이너에 적용한다. 실시간 활동 판정은 선택 문자열을 굽지 않는다.

예산은 JS가 항목 사이에 양보하는 기준이다. 브라우저의 단일 HTML 파싱·레이아웃·paint를
5ms 안에 강제 종료하는 하드 실시간 보장은 아니다. 큰 페이지의 **완료까지 걸리는 시간**과
**그동안 메인 스레드가 연속으로 멈추는 시간**을 구분해서 측정해야 한다.

### 저장과 선택 보존

- 표시용 HTML/모델 출처를 분리한다. 폰트·정렬 같은 모델 속성만 바꾸는 명령도 실제 수정으로
  판정하며, 로컬 커밋 후 출처를 갱신해 같은 내용을 원격 갱신이 불필요하게 덮지 않게 한다.
- 전송 op는 live 요소의 참조가 아니라 해당 revision의 독립 스냅샷이다. 저장 응답을 기다리며
  다음 서식을 바꿔도 ACK의 공통 조상은 실제로 전송한 본문이다. 자기 revision의 정확한
  에코는 최신 로컬 편집을 되돌리지 않는다. 오래된 ACK/다른 문서의 ACK도 새 기준을 덮지 않는다.
- 이 경합은 기존 서식 런타임의 간헐적인 전체 굵게 실패 원인이었다. 저장 응답 동안 모델과
  호출자 payload를 일부러 바꾸는 결정적 회귀 검사로 선택 DOM/본문/글꼴 보존을 검사한다.

### 읽기 화질과 메모리

- 서버 버킷은 480/900/1600px. 저사양은 480px로 시작하되 최종 크기는 화면 폭 × pageScale ×
  DPR로 정한다(상한 1600). 읽기 화질 승급은 편집 DOM 생성과 무관하다.
- 보이는 쪽만 요청하고, 새 그림의 decode가 끝나야 교체한다. 승급 실패 시 기존 그림을
  유지한다. 최초 그림도 없으면 예산을 지키는 요소 렌더로 폴백한다.
- 보이는 쪽이 속한 8쪽 데이터 슬라이스만 예열하며, 저사양 전체 프리필은 재개하지 않는다.
  먼 데이터는 `evictFar`로 다시 lazy 처리하고 현재/선택/편집/그리기/렌더 작업 중인 쪽은
  보호한다. 편집 이력이 확인된 쪽은 원본 그림을 걷고 실제 내용을 준비한다.

### 재현과 검증

```bash
npm ci
npm run test:activation       # jsdom: 동작·데이터·수명 회귀 (레이아웃 성능 측정 아님)
npm run test:preview          # 실제 JPEG 워커 테스트에는 worker Python 의존성이 필요

npm run test:editlag

npx playwright install chromium
npm run bench:activation     # 실제 Chromium, CPU 4배 감속
# 이미 설치된 브라우저를 쓰려면 SDY_CHROMIUM_PATH=/path/to/chromium
# CI 실행 인자 예: SDY_CHROMIUM_ARGS='["--no-sandbox","--disable-dev-shm-usage","--disable-gpu"]'
```

Chromium 검사는 실제 앱 HTML/CSS와 로컬 가짜 API/미리보기 이미지를 사용한다. 외부 웹폰트는
차단한 fallback-font 환경, 1280×900/DPR 1, 36문단 × 60단어 재현 페이지다. 기본 실행은
GPU를 끈 headless 소프트웨어 렌더링이다. 첫 클릭 선택, 레이아웃/스타일/긴 태스크/rAF 간격,
실제 입력·undo/redo·휠, 모바일 터치 에뮬레이션의 스크롤/선택/편집을 검사한다.

측정 중에는 페이지 내부에서 시간을 재고 결과를 내보낸다. 네이티브 마우스 입력 외의 DOM
조회/폴링은 측정 구간 밖으로 뺀다. 테스트의 스크롤 준비도 `curPageIdx`(즉시 변경됨)가 아니라
실제 뷰포트가 smooth-scroll 목표에 도착했는지로 판정한다. 서버리스 Chromium의 SwiftShader
경로에서는 스크립트/레이아웃과 무관한 긴 프레임도 관측됐으므로, 아래 비교는 같은 소프트웨어
렌더링 설정에서 이전 JS/CSS만 교체해 수행한 통제 측정이다.

2026-09-06 관측: 이전 클라이언트는 첫 클릭 선택 0개, 레이아웃 2,027회, 최악 긴 태스크
1,861ms / 프레임 간격 1,859ms였다. 수정 후 마지막 두 번의 검사에서는 첫 클릭 선택 1개,
레이아웃 64회, 최악 긴 태스크 58~69ms / 프레임 간격 64~72ms, 준비 완료 540~581ms였다.
이는 해당 합성 문서와 테스트 머신의 관측값이다. 사용자 원본 문서나 모든 기기의 성능 보장으로
일반화하지 않는다. 전체 strict 테스트 54개 그룹과 전환 회귀 57개 항목을 별도로 검사한다.

범위: 준비 중 일반 드래그는 재생하지 않고 취소하며, 키보드/IME 입력을 미리 버퍼링하지 않는다.
펜 샘플은 상한을 두고 보존한다. 실제 iOS/Android 기기, 외부 웹폰트의 네이티브 로딩 타이밍과
개별 사용자 원본 문서는 별도 실기기 확인 대상이다(폰트 캐시 무효화 자체는 DOM 회귀로 검사).

## 문제

예전 `renderPages()` 는 노트를 열 때 **문서의 모든 쪽**에 대해

- `.page-wrap` + `.page-label` + `.page-del` + `.paper` + 레이어 6개 (쪽당 약 10 노드)
- `pageObserver.observe(paper)` / `pageUnloader.observe(paper)` (쪽당 2회)

를 만들었다. 500쪽이면 노드 5천 개 + 관찰 1000회 + 종이 500장 레이아웃이라
**여는 순간 화면이 멎었다.** 요소(글상자·그림)만 가상화하고 종이는 전부 만들었기
때문에, 쪽수가 늘면 비용이 그대로 선형으로 늘었다.

부수 문제도 있었다.

- `IntersectionObserver` 는 transform 조상(에디터 슬라이드인) 아래나 먼 쪽으로 점프할 때
  콜백을 놓쳐 **빈 종이**가 남는 회귀가 반복됐다.
- 현재 쪽 표시·표 다시 그리기·핀·찾기·단어 분석이 전부 `doc.pages` 전체를 훑었다.
- `layoutPages()` 는 매 확대/축소마다 500개 `.page-wrap` 을 배열 순서로 재배치했다.

## 지금 구조 — 창(window) 두 개

```
#pagesStage  (높이 = 전체 쪽수 × (종이 높이 + 간격) × 배율)   ← 스크롤 길이는 항상 정확
│
├── .page-wrap[data-page-idx=118]   ┐
├── .page-wrap[data-page-idx=119]   │ 셸 창 = 화면에 걸치는 쪽 ± shellPad()(일반 2 / 저사양 0)
├── .page-wrap[data-page-idx=120]   │        (상한 shellMax()=일반 24 / 저사양 8)
├── .page-wrap[data-page-idx=121]   │
├── .page-wrap[data-page-idx=122]   ┘
└── #addPageZone                              ← 맨 끝에 항상 하나
```

- **셸 창(종이)**: `syncPageShells()` 가 `scrollTop`/`clientHeight` 로 보이는 범위를
  *계산*해 그 범위 ±`shellPad()` 만 `ensurePageShell()` 로 올리고, 나머지는
  `unmountPageShell()` 로 내린다. 스크롤 프레임마다 불러도 되는 싼 연산이다.
- **요소 창(내용)**: `maintainPageWindow(center, immediate)` 가 현재 쪽
  ±`renderRadius()`(일반 1 / 저사양 0) 만 `renderPageEls()` 로 그리고,
  ±`keepRadius()`(일반 2 / 저사양 1) 밖은 `unloadPage()` 로 레이어를 비운다.

종이는 `position:absolute` + `top = i*(h+gap)*scale` 로 놓는다. **자리를 계산으로
정하므로 앞쪽 종이가 DOM 에 없어도 위치가 밀리지 않는다** — 스페이서가 필요 없고,
5쪽이든 5000쪽이든 DOM 비용이 같다.

### 스크롤 중 프레임 예산

```
scroll ─rAF─▶ onEditorScroll()
                ├─ mostVisiblePageIndex()   현재 쪽 판정(노출 면적 비교)
                ├─ syncPageShells()         종이만: 매 프레임, 값싸게
                └─ maintainPageWindow(idx,false)
                     ├─ immediate            → 바로 채움 (점프·복원·강제 페인트)
                     ├─ 마지막 채움 후 fillMaxGap()(일반 220 / 저사양 160ms) 경과 → 바로 한 번 채움
                     └─ 그 외                → fillIdle()(일반 90 / 저사양 70ms) 디바운스 후 채움
```

디바운스만 걸면 계속 스크롤하는 동안 백지가 되고, 매 프레임 그리면 그게 곧 렉이다.
둘을 섞어 **관성 스크롤 중에도 최소 220ms 마다 한 번은 내용이 채워진다.**

## 불변 조건 (다른 기능을 건드리지 않기 위한 규칙)

1. **문서 데이터는 절대 건드리지 않는다.** `unmountPageShell()` / `unloadPage()` /
   `clearPageEls()` 어디에도 `doc.pages` 가 나오면 안 된다. 화면에서 내려간 쪽도
   데이터는 100% 남고, 저장·동기화·AI 스냅샷·내보내기(PDF/발표)는 전 쪽 데이터를 쓴다.
2. **작업 중인 쪽은 내리지 않는다.** `canUnloadPage()` 가 현재 쪽,
   `.tb.edit/.sel/.msel`(편집·선택), 활성 표(`activeTbl`), 그리는 중(`drawing`)을 막는다.
3. **창 밖의 쪽은 `paperAt()` 이 `null`** 이다. 호출부는 `paperQ(i, sel)` 로 방어한다
   (`paperAt(i).querySelector(...)` 처럼 바로 체이닝하면 안 된다 — 계약 테스트가 막는다).
4. **쪽 번호로만 찾는다.** `document.querySelectorAll('.page-wrap')[i]` 같은 배열
   순서 접근은 금지. 올라와 있는 종이는 `mountedShells: Map<pageIdx, wrap>` 이 관리하고,
   이동은 `scrollPageIntoView(pi, behavior)` 하나로 통일했다.
5. **새로 올라온 종이는 현재 모드를 물려받는다.** `buildPageShell()` 이 현재 쪽 강조
   (`focused` / `aria-current`), 종이 무늬(`paper-*`), 펜 모드(`drawing`)를 붙인다.
6. **화면 상태는 다시 그릴 때 복원된다.** 찾기 하이라이트(`paintFindHits`)와 단어 분석
   색칠(`wfPaintPage`)은 `renderPageEls()` 의 `finish()` 에서 그 쪽만 다시 칠한다.
   그래서 찾기·단어분석 중이라고 500쪽을 통째로 붙잡을 필요가 없다.

| `layoutPages()` 가 `.page-wrap` 전부 재배치 | `mountedShells` 만, 자리는 쪽 번호로 계산 |
| `updatePageInfo()` 가 전 종이 순회(배열 인덱스) | 올라온 종이만, 쪽 번호로 판정 |
| `renderAllTblDivs` / `renderAllPins` 가 전 쪽 순회 | `renderedPages` / `mountedShells` 만 |
| `wfPaint` 가 전 쪽 순회 | 올라온 쪽만 + 되돌아온 쪽은 렌더 때 복원 |
| `paperAt()` 이 쪽마다 `querySelector` | `mountedShells.get()` (O(1)) |
| `sanitizePageEls()` O(n²) 를 렌더할 때마다 | `WeakSet` 으로 배열마다 한 번만 |
| `elPlainText()` 가 매번 HTML 파싱 | `WeakMap` 캐시(html 이 바뀌면 자동 무효) |

## 여는 속도 (14.29.4) — 가상화 다음에 남아 있던 비용

쪽 가상화로 "그리는 일"은 창 크기로 고정됐는데, **열기 자체가 여전히 느렸다.**
그리기와 무관하게 *전체 문서를 훑는* 일이 열기 경로에 남아 있었기 때문이다.
느린 기기일수록 이 부분이 그대로 체감 지연이 된다. 아래 여섯 군데를 걷어냈다.

| 무엇이 느렸나 | 어떻게 바꿨나 |
|---|---|
| `getCfg()` 가 부를 때마다 수 MB `nb_*` JSON 을 다시 파싱 (열 때만 6~8회) | 저장된 **원문 문자열이 같으면** 파싱 결과 재사용(한 칸 캐시). 반환은 항상 얕은 복사본 |
| `openNB()` 가 **전 쪽**의 표 × 요소를 훑어 격자선 생성 | `ensureTableGrid(pi)` — 그 쪽을 처음 그릴 때 한 번만 |
| `_normalizePaletteHtml()` 이 글상자마다 DOM 파싱 | 색 지정이 든 html 만 파싱(`_PAL_RE`), 나머지는 그대로 반환 |
| 슬라이스 요청이 `no-store` — 늘 본문을 통째로 다시 받음 | `no-cache`(항상 재검증) + 서버 **ETag** → 안 바뀌었으면 **304 · 본문 0바이트** |
| 워커가 같은 `.s{n}.gz` 를 열 때마다 디스크에서 읽음 | ETag 를 키로 한 메모리 LRU 캐시(`SDY_SLICE_CACHE_MAX`, 기본 512) |
| 여는 즉시 나머지 슬라이스를 4갈래로 내려받아 첫 페인트와 경쟁 | `requestIdleCallback` 으로 **첫 화면이 그려진 뒤** 시작 (받는 양은 동일) |

### 안전 규칙

- **데이터·화면 결과는 바뀌지 않는다.** 전부 "같은 결과를 더 적은 일로"다.
- 설정 캐시는 *원문 문자열*을 비교하므로 저장·다른 탭의 변경도 놓치지 않는다.
  `setCfg()` 는 저장하며 캐시를 버리고, `migrate()` 는 캐시된 배열을 `slice()`
  해서 넘긴다 — 편집이 "디스크에 저장된 값"의 캐시를 오염시킬 수 없다.
- ETag 는 `(수정시각ns, 크기)` 라 **저장(POST) 하면 반드시 달라진다.** 워커 메모리
  캐시도 ETag 를 키에 넣으므로 오래된 본문이 나갈 길이 없다. 저장 경로는 무수정.
- 프록시(`workerProxy.js`)는 `if-none-match` 를 워커로, `etag` 를 브라우저로
  전달하고 304 에는 본문을 붙이지 않는다.

```bash
npm run test:openfast   # test/note_open_fast_contract.mjs · 33개
```

가짜 워커를 세워 프록시가 실제로 200+ETag → 304(본문 0바이트) 를 내는지,
설정 캐시가 저장·외부 변경을 놓치지 않는지까지 실행으로 확인한다.

## 스크롤이 버벅이던 진짜 이유 (14.30.1) — '그리는 양'이 아니라 '훑는 횟수'

쪽 가상화로 DOM 에 올리는 종이 수는 이미 작았는데도 **그림이 많은 논문은
스크롤이 초 단위로 멎었다.** 프로파일(jsdom + `--cpu-prof`)을 떠 보니 원인은
그리는 비용이 아니라, **문서 전체를 훑는 선택자 질의가 스크롤·렌더 경로에서
반복**되는 것이었다. 쪽 수가 아니라 *쪽 안의 요소 수*에 비례해 터지는 비용이라
가상화로는 잡히지 않았다 — 논문은 글상자마다 단어 span 이 수십 개다.

측정(40쪽 × 쪽당 37요소·476 span, jsdom):

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 스크롤 프레임 p95 | **5,913ms** | **169ms** |
| 최악 프레임 | **35,319ms** | **307ms** |

| 무엇이 느렸나 | 어떻게 바꿨나 |
|---|---|
| `liftLayers()` 가 `#pagesStage .paper` **전부** × 종이 subtree 하위선택자 3개. 게다가 MutationObserver 가 `#pagesStage` 아래 **모든** class 변경마다(빈 상자 `empty`·가져온 상자 `tight`·형광펜 띠·현재 쪽 `focused` …) 이걸 불러, 쪽 하나 그리는 동안 수백 번 전수 조사가 겹쳤다 — **스크롤 시간의 90%** | ① 올라와 있는 종이(`mountedShells`)만 ② 레이어의 **직계 자식**만 확인(`.tb`/`.paper-img`/`.stroke-g` 는 언제나 직계 자식이라 판정 결과 동일) ③ 관찰자는 선택 관련 변경만 골라 **그 종이만**, 프레임당 한 번(rAF) |

| `document.querySelector('#pagesStage .tb.edit[data-id=…]')` — 편집 상자는 최대 하나인데 원격 op·실시간 표시 타이머마다 subtree 전체를 훑었다 | `_activeEditBox()` 한 칸 캐시. `edit` 가 붙고 떨어지는 순간(관찰자 + 동기 경로)에만 무효화 |
| `decodeTextMarkup()` 이 `data-*` 서식이 하나도 없는 html 까지 DOM 파싱 | 표식 정규식(`_DEC_RE`)에 걸릴 때만 파싱. 없으면 원문 그대로 반환(결과 동일) |
| `paintTblCellSelection()` 이 칸을 하나도 안 골랐을 때도 `#pagesStage` 전체에서 `.tbl-cell-sel` 을 찾았다 | 칠해 둔 칸을 배열로 기억해 그것만 되돌린다 |

### 안전 규칙

- **화면 결과와 문서 데이터는 그대로다.** 전부 "같은 결과를 더 적은 일로"다.
- 캐시는 전부 **자기 검증형**이다. `findElLoc` 은 반환 전에 그 자리를 확인하고,
  편집 상자 캐시는 `isConnected` + `edit` 클래스를 다시 본다. 그래서 캐시를
  무효화할 곳을 빠뜨려도 틀린 답이 나갈 수 없다.
- `MutationObserver` 는 마이크로태스크라 같은 실행 흐름 안에서는 아직 오지
  않는다 → `edit` 를 켜고 끄는 동기 경로에서도 캐시를 즉시 갱신한다.

```bash

```

실제 서버 + jsdom 으로 '배경 래스터 + 그림 + 단어 span 글상자'가 든 논문형
문서를 열고, 사람이 굴리듯 프레임 단위로 스크롤하며 **프레임 시간**을 잰다.

## 어크로뱃처럼 — '읽기 우선' 구조 (20.0)

14.30.1 까지의 최적화는 전부 **편집 요소 DOM 을 더 적게·더 늦게 만드는** 방향이었다.
그런데 논문은 쪽 하나가 이미 무겁다.

```
논문 1쪽 = 배경 래스터 1 + 그림 2~3 + 문단 글상자 30~40개
         → 글상자마다 단어 span 10~20개 = 쪽당 DOM 500~800 노드
```

가상화로 "쪽 수"는 창 크기로 고정했지만, **쪽 '안'의 비용**은 그대로 남는다.
읽기만 할 때조차 그 DOM 을 다 만들어야 비로소 글자가 보였다. 이게 '열면 한참 걸리고,
스크롤이 손끝을 안 따라오고, 브라우저가 응답 없음으로 뜨던' 마지막 원인이다.
요소 수에 비례하는 비용이라 쪽 가상화로는 원리적으로 잡을 수 없다.

### 순서를 뒤집는다

어도비 어크로뱃이 500쪽 PDF 를 즉시 넘기는 이유는 단순하다 — **읽는 동안에는
쪽이 그냥 그림 한 장**이고, 편집 기능은 건드릴 때 붙는다. 같은 구조로 간다.

```
종이가 화면에 올라옴
   │
   ├─ 읽기 상태 (기본)   .layer-preview  <img> 한 장         ← DOM 1 노드
   │      /api/import/page/<ref>/<쪽>?w=900
   │
   └─ 편집 상태 (건드렸을 때만)  activatePage(i)
          renderPageEls(i) 로 진짜 요소를 올리고
          finish() 에서 그림을 걷는다 (깜빡임 없이 교대)
```

| | 예전 | 지금 |
|---|---|---|
| 읽는 쪽의 DOM | 500~800 노드 | **1 노드** (`<img>`) |
| 첫 글자가 보이기까지 | 요소를 다 그린 뒤 | 그림이 도착하는 즉시 |
| 스크롤 프레임 p95 | 166ms | **19ms** |
| 최악 프레임 | 179ms | **21ms** |

(`page_preview_runtime.mjs` · 40쪽 × 쪽당 35요소·476 span, jsdom 실측.
 같은 문서를 요소 경로로 열면 위 왼쪽 값이 나온다.)

### 편집 상태로 깨우는 순간

읽기 상태는 "아직 아무것도 안 한 쪽"일 뿐이다. 아래 중 하나라도 일어나면
그 쪽은 즉시 편집 상태가 되고, 그 뒤로는 예전과 100% 같게 동작한다.

- 종이를 누름 (`onPaperDown` / 배치·메모 캡처 핸들러)
- 펜·형광펜, 글상자 도구, 메모 붙이기, 그림·수식 배치, 표 배치
- 찾기, 단어 분석 (글자 DOM 위에 칠해야 하므로 보이는 쪽을 깨운다)
- 이미 깨운 쪽 / 편집한 적 있는 쪽은 새로 올라와도 계속 편집 상태

### 서버 — 쪽 그림 굽기

```
GET /api/import/page/<ref>/<pno>?w=900|1600
```

원본 PDF(`<ref>.src`)를 그대로 렌더한다. 배경 굽기(`_render_hi_bg`)와 달리
**redact 를 하지 않는다** — 글자까지 포함한 쪽 전체가 목적이기 때문이다.

- 파일 이름이 `sha1(ref:쪽:폭)` 인 **순수 함수** → 한 번 구우면 재사용,
  응답은 `max-age=31536000, immutable` 이라 두 번째부터는 네트워크도 안 탄다.
- 요청 폭은 `PREVIEW_WIDTHS(900 / 1600)` 로 스냅한다. 확대하면 1600 을 쓰고,
  임의의 폭으로 무한히 굽지 않아 캐시 적중률이 유지된다.
- 같은 쪽에 요청이 겹쳐도 쪽별 락 + 이중 확인으로 **한 번만** 굽는다.
- 굽기는 `.tmp` 에 쓰고 `os.replace` — 반쯤 쓴 파일이 캐시될 수 없다.
- 실측 55ms/쪽(A4 900px). 첫 열람에서만 들고, 그 뒤로는 0 이다.

### 안전 규칙 (이 구조에서 절대 깨지면 안 되는 것)

1. **문서 데이터는 그대로다.** 미리보기 경로(`mountPagePreview`/`dropPagePreview`/
   `previewURL`)는 `doc.pages` 를 읽지도 쓰지도 않는다. 저장·동기화·AI 스냅샷·
   내보내기(PDF/발표)·번역은 예전과 똑같이 **전 쪽 데이터**를 쓴다.
2. **편집한 쪽은 원본 그림으로 되돌아가지 않는다.** `markPageEdited()` 가
   `pg.edited` 를 문서에 남기고, 이 표시는 서버 슬라이스와 로컬 저장에 함께
   실려 **다시 열어도 유지**된다. `mountPagePreview` 는 `pageEdited(pi)` 면
   즉시 거절한다 — 편집분이 원본 그림에 가려질 길이 없다.
3. **한 번 깨운 쪽은 계속 편집 상태다.** 요소 DOM 을 회수(`unloadPage`)해도
   활성 표시는 남긴다. 되돌리면 그 쪽 편집이 가려질 수 있기 때문이다.
4. **그림을 못 받으면 조용히 예전 경로로 돌아간다.** `<img>` 가 실패하면 그 쪽은
   `renderPageEls` 로 폴백하고, 세 번 실패하면 그 문서 전체를 요소 경로로 돌린다.
   가져오기가 아닌 노트, 원본(`.src`)이 만료된 문서, 옛 서버 어디서도 기능 손실이 없다.

```bash
npm run test:preview
```

런타임 쪽은 가짜 워커로 슬라이스와 쪽 그림을 내주고, 실제로

- 읽는 동안 글상자 DOM 이 **0개**인가 (그림만으로 보이는가)
- 스크롤 p95 < 300ms 인가
- 건드린 쪽만 편집 요소가 올라오고 그 쪽 그림은 걷히는가
- 건드리지 않은 이웃 쪽은 읽기 상태 그대로인가
- 문서 데이터가 전 쪽 온전한가

를 확인한다.

## 저사양 기기에서 더 빨리 — '똥컴 경량 모드' (22.0 / 14.33.0)

위 두 설계(14.29 셸 가상화 → 20.0 읽기 우선)는 **좋은 기기 기준**의 최적화다.
똥컴에서는 여전히 ① 장식(오로라·blur·집게 애니메이션)이 프레임을 먹고, ② 쪽 그림
900px·셸 ±2가 아깝고, ③ 열자마자 나머지 슬라이스 프리필이 네트워크/파싱을 끌고 간다.

그래서 판정이 나면 `body.sdy-turbo` 를 붙여 **같은 결과를 더 작은 창·더 싼 그림·더
적은 장식**으로 만든다.
