# 코드 고치는 원칙 — "틀린 부분은 지우고, 그 자리에 정확한 코드를 쓴다"

> 이 문서는 유지보수 규칙이다. 버그를 고칠 때 **줄을 많이 쌓아서 문제를 덮는**
> 방식이 아니라, **틀린 코드를 정확히 지우고 올바른 코드로 바꾸는** 방식만
> 쓴다. 새 기능보다 수정을 할 일이 훨씬 많은 이 코드베이스(단일 sdynotes.js
> 약 2.8만 줄)에서는 "고치는 방식" 자체가 품질이다.

## 원칙 (순서대로)

1. **먼저 재현, 다음 수정.** 고치기 전에 실패하는 최소 테스트를 먼저 만든다.
   - 빠른 테스트 우선: 정적 계약(소스 패턴 검사, `test/*_contract.mjs`) 또는
     jsdom 런타임(`test/*_runtime.mjs`, 서버만 띄우면 됨 — AI 키·Python 워커 불필요).
   - 실 브라우저·실 모델이 필요한 테스트는 최후의 수단이다. 시간을 많이
     쓰는 테스트는 만들지도 돌리지도 않는다 — 돌지 않는 테스트는 없는 것보다 못하다.
2. **원인 줄을 찾을 때까지 읽는다.** 증상(예: "상자가 사라진다")이 보이는
   곳이 아니라, 데이터를 실제로 지우는 줄까지 호출 경로를 끝까지 추적한다.
   브라우저에서 못 잡으면 jsdom 으로 같은 경로를 재현한다.
3. **틀린 코드는 지운다. 덧붙이지 않는다.** 잘못된 조건·잘라 붙이기·덮어쓰기를
   발견하면 그 줄을 지우고 정확한 코드를 그 자리에 쓴다.
   - 금지: 원인 코드를 남겨 두고 어딘가(다른 레이어·이벤트 뒤·타이머 뒤)에서
     "되돌리는" 보정 코드 추가. 두 코드가 서로 싸우며 새 버그를 낳는다.
   - 금지: 겉모습만 가리는 가드(`try/cwrap` 으로 삼키기, 조건 하나 더 얹기).
   - 지운 자리에는 **왜 지웠는지** 한 줄을 남긴다(관례: `// 14.x.y · …`).
4. **판단은 한 곳에서.** 같은 규칙(예: "중복 상자는 지운다")이 두 군데에
   흩어져 있으면 한쪽만 고쳐지고 다른 쪽이 버그를 되살린다. 규칙이 쓰이는
   모든 곳(렌더·저장·동기화)을 함께 고치거나, 규칙 자체를 함수 하나로 모은다.
5. **회귀 테스트로 못 박는다.** 재현 테스트를 `test/` 에 남기고
   `package.json` 의 `test:*` 그룹에 넣는다(`npm test` 러너가 자동으로 인식).
6. **관련 그룹만 빠르게 검증.** 전체 스위트는 CI 에 맡긴다. 수정한 영역의
   그룹(예: `npm run test:ai`, `test:pages`)만 돌린다.

## 반례 — 이렇게 고치지 않는다

| 나쁜 수정 | 왜 나쁜가 |
|---|---|
| 사라진 상자를 `setTimeout` 뒤에 다시 그려 주는 보정 | 원인(지우는 코드)이 살아 있어 다른 상자가 계속 사라진다 |
| `if (사라졌으면) 복구()` 분기 추가 | "사라짐"이 정상 경우(사용자 삭제)와 구분 안 되어 삭제가 안 된다 |
| 새 레이어에서 좌표를 다시 계산해 겹침을 가림 | 원본 좌표가 틀린 채 남아 다른 화면(미리보기·내보내기)에서 깨진다 |
| 파일 하나를 통째로 재작성 | 리뷰·이력 추적이 불가능해진다. diff 는 최소여야 한다 |

## 실제 사례 (14.23.1)

### ① 논문 읽다가 텍스트상자를 누르면 상자가 사라진다

- **원인**: `sanitizePageEls`(sdynotes.js)가 "다른 글상자와 88% 이상 겹친다"는
  이유만으로 상자를 삭제하고, `renderPageEls`·저장 경로가 그 결과를
  **문서 데이터에 다시 썼다**. 가져온 문서의 이중 추출 중복을 지우려던 규칙이
  사용자가 일부러 겹쳐 놓은 상자(캡션·메모·번역 겹칩)까지 지운 것.
- **수정**: 텍스트 상자끼리는 **겹침 + 글 내용이 사실상 같은 경우에만** 중복으로
  본다(`_elSameText` 추가, 조건 한 줄 교체). 지우는 규칙 자체를 고쳤지,
  사라진 상자를 되살리는 보정 코드는 넣지 않았다.
- **회귀**: `test/ai_import_lazy_runtime.mjs` — 큰 상자 위에 겹쳐 놓은 작은
  상자가 페이지 왕복(재렌더) 뒤에도 살아 있는지 확인.

### ② 여러 쪽의 문서가 한 쪽에 겹쳐져 보인다

- **원인**: `upsertEl` 이 동기 op 의 쪽 번호가 문서 범위를 벗어나면
  `Math.min(page, 마지막쪽)` 으로 **마지막 쪽에 끼워 넣었다**. 쪽이 늘었다
  줄어드는 동기 과정에서 먼 쪽의 상자들이 한 쪽에 쌓여 보였다.
- **수정**: 범위 밖의 op 는 **무시**한다(잘라 붙이는 줄 삭제 → 범위 검사 한 줄).
- **회귀**: 같은 파일의 "다른 쪽 글이 한 쪽에 섞이지 않는다" 검사.

### ③ 해돌이 '이 페이지' 정리가 첫 페이지처럼 나온다

- **원인**: 브라우저는 보는 쪽 글만 보내지만, **서버 프롬프트가 그 글이
  '문서 전체'인지 '지금 보는 한 쪽'인지 몰랐다**. 모델이 한 쪽분량을 받아도
  문서 전체 개요(서론→결론)로 답해 "첫 페이지만 요약했다"고 보인 것.
- **수정**: 요청에 `scope` 를 실어 보내고(`run`/`warmOne`), 서버가
  `scope==='page'` 면 프롬프트에 "지금 본문은 한 쪽 분량" 한 줄을 붙인다
  (`aiMessages`). 캐시 키에도 범위를 포함해 같은 글·다른 범위가 같은 답을
  재활용하지 않게 했다. 프런트 다리(`__sdyAiBridge.text('page')`)는
  스크롤·쪽 이동 모두 이미 정확함을 테스트로 확인했다(고칠 곳이 아니었다).
- **회귀**: `test/ai_page_scope_runtime.mjs`, `test/ai_import_lazy_runtime.mjs`,
  `test/ai_frontend_contract.mjs`(범위 동봉 검사), `npm run test:ai`.

이 사례들의 공통점: **수정 위치는 원인이 발생한 한두 줄**이었고, 코드는
전체적으로 줄어들거나 그대로다. "무엇을 지웠는지"가 diff 의 본체다.
